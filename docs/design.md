# Monkey fine-tuning — design

**Date:** 2026-09-27
**Related:** MonkeePawLLM `docs/superpowers/specs/2026-09-26-core-engine-design.md`

## Goal

Make Monkey, MonkeyPaw's own model, by fine-tuning Qwen2.5-Coder so that it:

- runs well on an 8 GB RAM laptop with no GPU, with CPU threads and context size adjustable per request (battery, responsiveness);
- uses MonkeyPaw's tools reliably, especially small `edit_file` changes instead of rewriting whole files;
- trains for free, overnight, and survives interruptions.

MonkeeLLM (the from-scratch model) stays a separate learning project.

## Decisions

| Decision | Choice | Why |
|---|---|---|
| Base models | Qwen2.5-Coder 0.5B and 1.5B Instruct | Apache 2.0 (3B is research-only). 0.5B for `light`, 1.5B for `balanced`/`max`. |
| Method | LoRA r=16 on all linear layers over a 4-bit base (Unsloth) | Fits a free T4 (16 GB), about 2× faster than plain PEFT. Low risk of damaging what the base model already knows. |
| Training platform | Kaggle, *Save & Run All* | Free T4, about 30 h/week, runs in the background up to 12 h. |
| Resume | Checkpoint on Hugging Face (private) every 20 min, plus a clean stop at 11 h | Platform-independent. At most ~20 min lost. |
| Laptop runtime | Ollama with our Modelfile (Q4_K_M for 1.5B, Q8_0 for 0.5B) | MonkeyPaw already talks to Ollama and sends `num_thread`/`num_ctx` per request, so resource limits need no new code. |
| Data v1 | Open datasets only (CommitPackFT, Self-OSS-Instruct, xLAM) | Permissive licenses. Nothing generated by Claude. |

## Prompt format: one source of truth

Training text is rendered by `render.py`, and at runtime Ollama renders it with `OLLAMA_TEMPLATE`. The two are kept byte-identical (`tests/test_render.py`). The template has the same structure as Ollama's official qwen2.5-coder template, so Ollama's tool-call parser works unchanged.

Rules that follow from the template:
- An assistant turn has either text or tool calls, never both (the template drops tool calls when there is text).
- One tool call per turn in MonkeyPaw sessions. xLAM examples may have several in one `<tool_call>` block, which Ollama also parses.
- **Known mismatch:** Ollama re-renders past tool-call arguments in history as compact JSON with sorted keys, while Monkey generates them in natural order (`path, old_string, new_string`). This only affects earlier turns, and we accepted it so the model can write `old_string` before `new_string`.

## Data

**CommitPackFT → agent sessions (75%).** Each real commit becomes:

```
user: <commit subject/body> [+ file path, 65% of the time]
assistant: grep(<word from the request>)          # only when no path is given
assistant: read_file(path)
assistant: edit_file(path, old, new) × 1–4         # minimal hunks, old_string unique
assistant: short summary
```

- Tool results come from running the calls in `sandbox.py`. The replay must reproduce the commit exactly, or the example is dropped.
- Grep patterns come only from words in the request, so the model never learns to search for things it couldn't know.
- 2–5 unrelated files from other commits are added to the workspace so searches have noise.
- Filtered out: commits that rename files, files over 250 lines or 12 KB, subjects under 3 words or starting with merge/bump/release/revert, and more than 4 hunks.
- A new file (empty before) becomes a `write_file` session.
- Language mix is weighted toward Python/JS/TS; see `sources/commitpack.py`.

**Self-OSS-Instruct (15%):** plain question → answer with tools available. This teaches Monkey not to call tools when none are needed, and keeps its general coding ability from drifting.

**xLAM (10%, optional, gated):** unseen API tools → correct calls. This teaches argument discipline in general.

**Loss mask:** only Monkey's own turns (tool calls, answers, `<|im_end|>`) are trained on. System, user and tool-result text is context only.

Smoke test on 3,000 real Python commits: 98% usable, median about 1,400 tokens, max about 2,300, so none are over the 4,096 training limit.

## Training

`train.py` is idempotent. It reads `status.json` in the `-train` repo:
`missing → fresh`, `training → resume last-checkpoint/`, `done → exit`.
A callback saves by time, uploads the checkpoint folder (adapter, optimizer, scheduler, RNG, data position), and stops cleanly at the time budget. HF Trainer's `resume_from_checkpoint` restores everything, including the data order.

Defaults: 1 epoch over ~24k sessions, lr 2e-4 cosine, 3% warmup, effective batch 16, 8-bit AdamW, fp16 on T4, `group_by_length` to limit padding.

## Lesson from v1: tool-call tokens must be trained directly

The first 0.5B run trained cleanly (loss 1.19 → 0.6) but produced garbage in Ollama. Qwen2.5-Coder has `<tool_call>` / `</tool_call>` as single tokens but was never trained to produce them: the base model gives the correct `<tool_call>` probability ~1e-10 (loss ≈ 23). LoRA adapts the transformer layers but can't change a token's embedding, and Qwen ties input and output embeddings, so after training it still reached only ~6e-5. It learned everything around the markers (average loss 0.13 elsewhere) but couldn't open a tool call, so free generation derailed and never reached `<|im_end|>`.

Fix (v2):
- `train.py` passes `trainable_token_indices={"embed_tokens": [<tool_call>, </tool_call>]}` to the LoRA config. That trains only those two embedding rows, which with tied weights also updates the output rows.
- `export.py` merges with PEFT (which applies the trained rows) instead of Unsloth's merge. It then measures P(`<tool_call>` as the first reply token) on held-out tasks and refuses to export below 0.5. The v1 model scores 0.0001.
- `train.py` prints the same check at the end of training.
- Each training run has a `version` in its config and its own `-v<N>-train` checkpoint repo, so a new run never resumes from, or skips because of, an old one.

## Evaluation

`evaluate.py` runs the model through Ollama (the real quantized model and prompt path) as an agent over held-out commit tasks in the sandbox, for up to 8 steps. It reports: finished, changed the right file, exact match with the commit, touched other files, rewrote a whole existing file, tool/format errors per task, and speed. Compare `qwen2.5-coder:*` against `monkey-*` to see whether fine-tuning helped. Exact match is strict (a commit message rarely fully specifies the change), so watch the trend, not the absolute number.

## What MonkeyPaw needs to match

1. Tool names, arguments and descriptions: `monkeytrain/tools.py`.
2. System prompt: `tools.SYSTEM_TEMPLATE`. MonkeyPaw's core spec says about 700 tokens with MONKEEPAW.md. Keep the rules section identical and append the rest.
3. Tool result wording: `sandbox.py` (numbered `read_file` lines as `%6d\t`, `Edited <path>: replaced 1 occurrence.`, `path:line:text` for grep, error texts).
4. Model tiers in `system/models.ts`: `light → monkey-0.5b`, `balanced`/`max → monkey-1.5b` once they beat the base models.

If any of these change in MonkeyPaw, update them here and retrain. The Modelfile template comes with the model.

## Not covered by v1 (next phases)

- **bash, web_search and web_fetch** get no training sessions: we can't produce realistic outputs for them from commits. Phase B (an open teacher model such as Qwen2.5-Coder-7B/14B running real tasks) and phase C (logged MonkeyPaw sessions) cover them.
- Multi-file changes, fixing a failed edit, and running tests: same.
- Evaluation of 0.5B/1.5B on the MonkeyPaw end-to-end smoke checklist happens once the TypeScript core exists.

## Risks

- Unsloth, TRL and transformers change fast. `train.py` uses only the stable parts (`FastLanguageModel`, the plain `Trainer`), and `export.py` searches for the GGUF file by pattern. The first 0.5B run is the end-to-end test.
- CommitPack requests are terse and sometimes vague. The model may learn to act on vague requests rather than ask. Phase C data corrects this.
